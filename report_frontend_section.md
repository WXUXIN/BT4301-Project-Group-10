# Frontend Dashboard — Report Section

## 4.X Production Dashboard: ChurnGuard

To operationalise the churn prediction system for business users, a browser-based dashboard named **ChurnGuard** was developed as a single-page application (`index.html`) served alongside the FastAPI backend. The dashboard provides a complete interface for viewing model predictions, exploring individual customer risk profiles, and initiating targeted retention outreach — without requiring users to interact with the API directly.

---

### 4.X.1 Architecture and Integration

The frontend is a self-contained HTML/CSS/JavaScript file that communicates with the FastAPI backend via `fetch` calls to the `/predict-batch` endpoint. On load, the application reads customer feature data from `latest_predictions_input.json`, submits it to the backend for scoring, and renders the results client-side.

A key design decision was the inclusion of a **Demo Mode** fallback. If the backend is unreachable — for instance, when the application is demonstrated without a running model server — the dashboard automatically switches to client-side heuristic scoring that approximates the XGBoost model's behaviour using the same input features (satisfaction score, complaint count, late payments, contract type, risk flag, and tenure segment). This ensures all dashboard features remain functional during presentations or development without requiring model artifacts to be present.

The API connection state is surfaced to the user through a status pill in the header bar, which displays:
- **API Connected** (green) when predictions are sourced from the live model
- **Demo Mode** (orange) when the client-side fallback is active
- **Not connected** (grey) before any predictions have been run

---

### 4.X.2 Key Features

#### Summary Statistics

Four summary cards are displayed at the top of the dashboard and update dynamically whenever filters are changed. These show: the total number of customers scored in the selected period, the count and percentage of customers flagged as at-risk (`churn_prediction = 1`), the count of high-risk customers alongside the medium-risk count, and the average churn probability across at-risk customers only. These cards give operators an immediate aggregate view of churn exposure without needing to inspect individual rows.

#### Period Selection

Customer records are divided into three consecutive periods, simulating the rolling monthly batches produced by the Airflow ETL pipeline. The dashboard defaults to **Period 3 (Latest)**, reflecting the most operationally relevant data. Users may switch to earlier periods or select all periods to review historical predictions. Switching periods re-filters already-scored predictions instantly, without re-calling the API.

#### Risk and Customer Filters

A toggle allows users to switch between **At-Risk Only** (default, showing customers where `churn_prediction = 1`) and **All Customers**. A live search field enables lookup by customer ID, applied on top of the period and risk filters. These controls allow a customer success team to quickly narrow down to the highest-priority cases within any given period.

#### Predictions Table

The main table presents each customer row with the following columns:

| Column | Description |
|---|---|
| Customer ID | Displayed in monospace for readability |
| Churn Probability | Inline visual bar and percentage, colour-coded by risk tier |
| Risk Tier | Colour-coded badge: red (high ≥ 0.6), orange (medium 0.3–0.6), green (low < 0.3) |
| Contract Type | Badge indicating Monthly, 1-Year, or 2-Year contract |
| Tenure Segment | Badge indicating Infant, Stable, Loyal, or Veteran tenure group |
| Actions | Email button (at-risk customers) and row expand toggle |

The probability bar provides an at-a-glance visual encoding of churn risk that is more interpretable than a raw percentage, particularly when scanning a large list of customers.

#### Expandable Customer Detail Panel

Each row can be expanded to reveal a detail panel showing the full feature profile of the customer. Numeric fields — satisfaction score, complaint count, service call frequency, and late payment count — are colour-coded to indicate severity (red if concerning, orange if moderate, green if healthy). The panel also displays the computed `high_risk_flag` status and a row of service subscription chips indicating which products the customer is enrolled in (Phone, Internet, Tech Support, Streaming TV, Streaming Movies, and Auto Pay), shown as active or inactive. This allows a retention agent to understand the context behind a prediction before deciding how to respond.

#### Retention Email Modal

For each customer flagged as at-risk, an **Email** button opens a modal pre-populated with a personalised retention message. The subject and body of the email are generated by matching the customer's feature profile against a priority-ordered set of conditions:

| Condition | Retention Angle |
|---|---|
| High risk, month-to-month contract | Offer a discount to switch to an annual plan |
| High risk, ≥ 2 complaints | Apology, service credit, dedicated account manager |
| High risk, ≥ 1 late payment | Flexible payment plan options |
| High risk, satisfaction ≤ 4 | Personal outreach to understand dissatisfaction |
| High risk (other) | Loyalty rewards and plan review |
| Medium risk | General check-in and plan optimisation |

All fields — recipient address, subject, and message body — are fully editable before sending. As this is a prototype, clicking **Send Email** does not dispatch a real email; instead, it closes the modal and displays a toast notification confirming the mock send. This simulates the end-to-end retention workflow without requiring email infrastructure.

#### CSV Export

An **Export CSV** button downloads the currently visible records as a comma-separated file, respecting the active period and risk filter. The exported file includes customer ID, churn probability, prediction, risk tier, contract, tenure segment, and key behavioural features. The filename encodes the active period and export date (e.g., `churn_latest_2026-04-05.csv`), facilitating audit trails and handoff to CRM or marketing systems.

---

### 4.X.3 Design Rationale

The dashboard was designed with operational use in mind rather than purely analytical exploration. Defaulting to the latest period and at-risk customers means a retention team opening the dashboard immediately sees the most actionable view — the customers most likely to churn in the current period — without needing to configure anything. The email modal reduces friction in the outreach workflow by pre-filling messages based on the specific risk drivers identified by the model, allowing agents to personalise communications at scale.

The decision to embed all logic in a single HTML file, with no build toolchain or external dependencies, was deliberate. It keeps the deployment footprint minimal — the frontend is served as a static file alongside the existing Docker container — and ensures it is straightforward to review, modify, and hand off.
